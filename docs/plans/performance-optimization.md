# 性能优化维护说明

## 目标查询

条件表情和面部互动按归一化名称建立目标索引，每次更新复用活跃层顺序，
使逐键查询的开销随查询键数和活跃层数增长，避免每个键扫描全部目标。
名称碰撞保留全部目标及源表顺序；配置替换、拖拽修改和重置必须使对应缓存失效。

## 录制准备

录制校验和分析通过可取消任务分片推进，完整校验两条轨道后才连接游戏对象。
分片减少单次回调集中工作，不保证总准备时间缩短；时间预算在检查点生效，
受时钟分辨率、GC 和检查点间隔影响，不是硬实时上限。

连续空差分共享只读快照，非空差分复制后修改。共享快照的统计按重复帧数累计，
不能改写前帧，也不能遗漏实际经过帧的命中次数。
只为选中轨道保留快照，未选轨道仍须完整校验。
持续变化的录制仍保留完整变化帧；文件读取、JSON 解析、游戏对象连接和绑定刷新仍同步执行。

播放状态和性能指标的接口约定见 [shape-key-system-api.md](shape-key-system-api.md)。

## 离线复测

需要 Python 和 `lupa`，在仓库根目录运行：

```powershell
python tools/profile_offline.py
```

结果默认写入 `local/performance/latest.json`，该目录由 Git 忽略。
需要保留不同版本结果时指定文件名：

```powershell
python tools/profile_offline.py --output local/performance/baseline.json
```

工具使用实际 Lua 模块和项目的 REFramework 替身，文件操作位于临时目录，不连接游戏。
查询与解码预热后测量五轮中位数；准备任务另测分片数量和最大分片耗时。
分配量与保留内存分别测量，分配量不能解释为泄漏。

对比时保持机器、录制、参数数量和测量条件一致。替身耗时不包含真实 SDK、渲染器或 GPU 开销，
不能换算为游戏 FPS；引擎调用次数仅用于定位重复操作，不能据此删减对象和索引校验。

## 游戏内验证

进入存档后测试条件渐变和面部拖拽，再播放录制，检查准备进度、暂停、跳转、循环和停止恢复。
预期混合顺序保持一致，停止后游戏动画恢复，准备取消后不会出现延迟播放。
在「设置与调试 → 性能 → 展开耗时详情」观察文件读取、准备分片和原版注入的最大耗时。
异常反馈包含录制名、操作、耗时与脚本错误。

## RE4R 运行时

网格通道名称、Profile 匹配和指纹随资源缓存。逐帧沿数字路径比对目标部件和网格的地址，
通道数和资源标识每 15 次完整核对一次；周期巡检按实际秒数执行，发现新增部件或资源变化后重新绑定。
零通道武器和投掷辅助网格不参与形态键签名。

表情层只写变化的通道。捏脸层与荒野相同使用惰性模式：捏脸值变化时整套重写，驱动、面捕、
条件规则和互动的值变化时只重写它们当前和上一次控制的键，外部控制释放后恢复基础值。
写入按网格排队，可写判断按网格和通道名列表缓存。

`ShapeKeySystem_Native.dll` 可用时，面部动画姿态、修正曲线、标定骨骼、crct 通道权重和部件
路径比对各用一次原生调用完成，写入按网格一次写出；插件不在或调用失败时回退到 Lua。

原生输入可用时跳过对应的备用面骨采样，数值为零也视为可用。
下巴等叠加贡献及被其他规则引用的共享骨骼继续采样。现有 Deform 输入优先读取，
缺项或读取异常时逐项回退；空索引和失败索引间隔两秒复核。

后台角色按各自网格匹配 Profile，显式绑定优先。没有输出任务的角色保留在角色列表，
新增匹配配置或外部驱动后恢复更新。切换编辑角色不改变其他角色的匹配依据。

### 游戏内耗时记录

同一台机器使用 Milltina 换模，头部 720、身体 63、头发 6 个通道，自动表情输出 47 项，
缺失下巴及四根眉毛骨。以主线 1.9.1 的计时版本为基线，与最终优化计时版本比较：

| 场景 | 基线平均耗时 | 优化后平均耗时 | 每帧节省 | 开销减少 |
|---|---:|---:|---:|---:|
| 待机 | 3.450 ms | 1.893 ms | 1.557 ms | 45.1% |
| 过场 | 3.766 ms | 1.958 ms | 1.808 ms | 48.0% |

这些数值统计 System 回调耗时，均包含测试计时开销。过场取样时长和面板操作不同，
后台角色数量随场景变化；表中给出各次录制的均值。整机帧率收益另用固定存档、镜头、
画质和相同过场比较 CPU、GPU 帧时间。

最终记录中，选中艾达后的稳定区间共有 2,313 帧，后台里昂每帧继续读取表情。
Deform 索引在约 30 秒内构建 16 次，失败数为零；该换模的现有表没有匹配输入，使用 extra-joint。

### 重建与回收的后续计划

一次长过场记录中，完整 Lua 垃圾回收耗时约 116 ms，回收前内存约 102 MiB。
后续按以下顺序处理：

1. 用发布包和轻量采样复测同一切换动作，分别记录未录制、短录制、长录制时的 Lua 内存和回收耗时，分离记录数据累积的影响。
2. 合并同一帧重复的重建通知。对象销毁前先停止写入并清除引用，再核对哪些回收可合并；逐一验证读档、过场跳过、角色切换和脚本重置。
3. 将重建中的名称解析、配置匹配和界面数据整理拆分计时。对占时较大的纯 Lua 工作复用缓存或分片，部件完成准备后恢复写入。

验收同时观察常态耗时、P95/P99、切换最大停顿、表情恢复时间和 Lua 内存回落，
并保持多角色独立驱动、非零权重持续写入及原生输入保护。
