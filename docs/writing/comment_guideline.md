# 代码注释规范

本规范适用于 ShapeKeySystem 的 Lua 源码注释（文件头注释、函数前注释、行内注释）。目标不是增加说明数量，而是保留能阻止错误维护的事实，让注释随代码长期成立。

由项目作者维护，未经允许不得随意改动。改编自 EFX-Editor 的 `docs/writing/comment_guideline.md`。

## 核心判断

一条注释应当回答至少一个非显然的问题：为什么必须这样做、谁拥有这项职责、哪些状态不能破坏，或兼容分支在什么条件下生效。

如果删去注释后，熟悉代码的维护者仍能从名称、参数和相邻实现直接得出同一结论，就应删除或缩短它。

## 应保留的内容

- 稳定的模块职责、所有权边界和明确不负责的事项。
- 非显然的维护约束：写入时机、引用生命周期、通道顺序、坐标系与符号约定、缓存失效、脏标记。
- 跨模块契约，例如谁负责放掉引擎对象引用、谁负责重扫、哪一层保证写入的值是浮点数。
- 兼容与回退行为，以及其触发条件。旧设置字段、旧文件路径只在实际决定兼容分支时保留。
- 生命周期要求，例如过场开始前必须放掉引用、hook 回调只记标记不做重活、绘制路径不得写入游戏。
- 因果关系和设计理由，而不是对下一行代码的复述。

## 应删除的内容

- 日期、版本历史、提交号、会话记录和改动过程。
- 探查来源、样本数量、实测过程、调查结论和旧实现的叙述。
- 已被代码直接表达的逐行说明、参数清单或 UI 控件清单。
- 过时的实现比较、猜测性结论，以及面向 AI 的辩解式措辞。
- 与面板文案重复的解释。

## 放置方式

### 文件头注释

只写稳定职责、重要所有权边界和少量全局维护约束。它应帮助维护者判断功能应放在哪里、哪些模块不能越权，而不应成为 API 清单、文件格式 schema 或开发日志。文件格式写在 `docs/plans/shape-key-system-api.md`，文件头只留入口。

```lua
-- ShapeKeySystem: blendshape weight writes.
--
-- Constraints:
-- - A mesh is not written until its weight buffer exists; writing earlier can freeze the game.
-- - Every value passed to the engine is a float (`w + 0.0`): a Lua integer reaches a
--   System.Single parameter as raw bits.
```

使用「Constraints」「维护约束」这类直白标题即可；避免抽象而不解释的术语。每条约束都应能对应当前代码中的长期行为。

### 函数前注释

仅在函数的名称和参数不足以表达时补充。优先说明输入的语义、关键副作用、返回或失败语义，以及调用方容易误用的条件。

```lua
-- Returns the fcParam joints for a list of param numbers; missing joints are skipped, not nil.
function S.joints(face, list)
```

不要把函数体翻译成自然语言，也不要重复显而易见的参数类型。

### 行内注释

贴近它解释的判断、赋值或循环，说明该处不能轻易改写的原因。适合记录优先级、单位、边界条件、回退语义和顺序要求；不适合给每个局部变量加说明。

```lua
-- pre-hook: references must be gone before the game destroys the cutscene actors
sdk.hook(m, function() pcall(on_release, name) end, nil)
```

## 常见维护约束

以下类型的事实通常值得保留，但应由最接近其所有者的模块说明：

- 形态键只在 `LateUpdateBehavior` 中、且权重缓冲区存在之后写入。
- 跨部件重建、过场结束时不得持有引擎对象引用（`Guard.lua`）。
- 传给引擎 `System.Single` 参数的值必须是浮点数。
- `require` 只在脚本加载阶段解析，模块必须在加载时引入，不得在帧回调中延迟引入。
- hook 回调可能一帧被调用多次，只记录标记，由每帧更新统一处理。
- 与 ArmorVariantManager 共存的约定：热键、共享输入屏蔽表、不替换 d2d 全局。

这些不是固定模板。只有当某条规则仍由当前实现承担、且删除后可能诱发错误重构时，才应写入注释。

## 措辞

- 用准确、可验证的陈述句，例如「重扫后保留同一网格的预热计数」，不要写「应该没问题」或「理论上」。
- 说明自动行为，而非凭空增加权限或限制。除非代码确实拒绝其他路径，否则不写「只有此处才能……」。
- 说明真实粒度。若只更新 `t.last`，不要笼统写成「重置目标」。
- 不确定的游戏行为不要伪装成规则；应先实测确认，或移至 `docs/plans/` 中的专题文档。
- 注释语言与所在文件一致，使用项目现有术语和模块名。

## 与测试和专题文档的边界

注释记录当前代码必须维持的行为，不替代测试、格式文档或排查记录。可执行检查放在 `tests/tests_*.lua`；较长的文件格式、迁移说明和探查证据放在 `docs/plans/`，代码中只保留必要入口。

## 审阅检查表

修改注释前后逐项确认：

1. 该注释是否描述当前实现，而非历史、样本或验证过程？
2. 它是否保留了职责边界、兼容语义或非显然维护约束？
3. 是否写在最接近该事实所有者的位置，且没有与其他注释重复？
4. 是否避免复述代码、面板文案和显而易见的类型信息？
5. 是否只修改注释，没有改变执行逻辑、字符串或数据结构？
6. 运行 `cd tests; python run.py`，各组 FAILS 与修改前一致；运行 `git diff --check`。工作区可能已有其他改动，审阅时只确认本次目标文件的 diff。
