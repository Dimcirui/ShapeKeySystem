# 提交信息规范

本规范适用于 ShapeKeySystem 的 commit 标题与正文。目标是让 `git log` 能直接回答「这次改了什么行为、为什么改」，并能作为发布说明的素材；证据、调查过程和验证记录不属于提交信息。改编自 EFX-Editor 的 `docs/writing/commit_guideline.md`。

判断标准沿用 [comment_guideline.md](comment_guideline.md)：只保留读者从 diff 里看不出、且会影响后续判断的事实。

## 核心判断

一条提交信息应当让没参与这次工作的人读完标题就知道改动的性质和作用对象，读完正文就知道原先哪里不对、现在怎样、有什么兼容影响。

如果删去正文后，标题加 diff 已足以得出同一结论，就不写正文。

## 标题

格式为 `type(scope): 摘要`，冒号为半角，摘要用中文，一句话，不加句号。

| type | 用途 |
|---|---|
| `feat` | 新功能、新增内置配置或信号 |
| `fix` | 修正插件行为错误 |
| `refactor` | 不改变行为的结构调整 |
| `perf` | 不改变行为的性能改进 |
| `docs` | 注释、README、设计文档、面板文案 |
| `test` | 离线测试 |
| `chore` | 版本号、部署与打包脚本、工程配置 |

- `scope` 写下文「拆分提交」里的类别。一次提交确实跨多个类别时省略 scope，不硬凑。
- 摘要写改动后的结果，不写过程。写「换装后保留未保存的映射修改」，不写「修复映射修改的问题」。
- 定版提交固定为 `chore(version): 定版 X.Y.Z`；合并提交为 `merge: 分支主题`。

## 正文

与标题之间空一行，按约 72 字符宽换行。只在以下内容存在时写：

- **原行为错在哪**：一句话讲清错误的读法或现象，不复述排查经过。
- **现在的行为**：玩家或文件格式层面能观察到的变化。
- **兼容影响**：设置字段改名并已迁移、旧路径不再读取、用户 profile 需要修改、绑定文件格式变化。
- **刻意不做的部分**：同一主题下明确留着没改、且读者容易以为改了的内容。

多项并列时用 `-` 列表，每项一到两行。一次提交通常不超过五行正文。关闭 issue 时在正文末尾写 `Closes #N`。

## 应删除的内容

- 调查过程与证据：实测记录、探查输出、截图对照、推导过程。去处是对应 issue 或 `docs/plans/`。
- 验证记录：「已实机验证」「未经实机验证」这类出处说明，以及逐项罗列的测试通过数。测试正常通过不写。
- diff 已经能看出的清单：改动文件列表、新增函数名、逐个字段的改名映射。
- 旧实现的长篇叙述、自我评价（「更清晰」「零风险」）和对本次提交形式的辩解。
- 日期、会话记录、阶段编号和面向 AI 的说明。

**例外**：`tests/` 中应跑但没跑的组，或已知仍失败的检查（除已记录在 CLAUDE.md 中的两个 gaze 检查外），写一行说明。这是读者需要知道的风险，不是验证记录。

## 拆分提交

按类别拆，不按单个发现拆。同一轮工作里属于同一类别的改动合成一次提交，哪怕它们是好几个互不相干的小改动。

| 类别 | scope | 范围 |
|---|---|---|
| 表情 | `expr` | profile 编译、信号字典、表情计算、眼球 |
| 捏脸 | `sculpt` | 捏脸层与捏脸预设 |
| 预设与绑定 | `preset` | 绑定文件、默认绑定、部件指纹 |
| 条件表情与互动 | `cond` | 条件定义、条件集、面部互动 |
| 扫描与写入安全 | `scene` | 找脸、找部件、写入时机、过场与换装处理 |
| 游戏适配器 | `adapter` | `ShapeKeySystem_Games/` 下的各游戏实现 |
| 面板 | `ui` | 面板页面、绘制后端、输入屏蔽、文本输入 |
| 外部接口 | `api` | 供其他插件调用的接口 |
| 内置数据 | `data` | `builtin/` 下的配置、别名表、装备名、面部导航图 |
| 工具 | `tools` | `tools/` 下的部署、安装、生成脚本 |
| 核心重构 | 省略 | 大范围结构调整 |
| 注释文档 | `docs` | 注释、README、设计文档 |

规则：

- **一件事只归一个类别。** 一个改动同时涉及扫描、表情和面板时，按它的主要目的归类，不要拆到几个类别里。
- **每个提交单独检出都能运行。** 拆分不得产生缺文件、缺模块或引用未定义名字的中间提交。
- **不同人的改动分开提交**，即使属于同一类别。
- **定版单独提交**：`chore(version): 定版 X.Y.Z`。
- **注释修缮不与逻辑改动混在同一次提交**：注释提交应能单独确认没有改变行为。

一次提交包含同一类别的多项改动时，正文按改动列出，不写解释为何合并的段落。

## 改写对照

标题只写「修复报错」，改为写出结果；正文补上原行为错在哪和兼容影响。

```text
# 前
fix：修复新增表情配置报错

# 后
fix(expr): 读取通道为空的表情配置

REFramework 把空 Lua 表写成 JSON null，新建的空配置读回时被当成无效文件跳过；
现在按空通道列表读取，已创建的空配置无需重建。
```

标题并列多个无关主题，改为拆分。

```text
# 前
Add ImGui draw backend and Chinese text input for the panel

# 后（两次提交）
feat(ui): 面板支持 ImGui 绘制后端
feat(ui): 文本框支持中文输入
```

## 自检

1. 只读标题，能否判断改动性质和作用对象。
2. 正文每一句是否都是 diff 里看不出的事实。
3. 是否残留证据、实测记录、测试通过数或验证出处。
4. 兼容影响（设置迁移、路径变化、用户文件需要修改）是否写明。
5. 改动是否只属于一个类别，且这次提交单独检出能运行。
