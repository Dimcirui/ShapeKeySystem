# Issue 书写规范

本规范适用于 ShapeKeySystem 的 issue 正文与评论。本项目的 issue 定位为开发笔记，不是讨论串：读者是日后回来查这件事的维护者，需要的是「做了什么、定了什么、哪些还没定」，而不是讨论经过。

措辞沿用 [comment_writing.md](comment_writing.md)：主语是本项目的模块、数据或结论；使用确定语气和书面语；不写自我评价。

## 核心判断

一条评论应当让维护者不读讨论经过就知道这件事的当前状态。设计细节写在 `docs/plans/` 的文档里，评论只留入口和结论。

如果一条内容已经写在文档、提交信息或 issue 正文里，评论中不再重复。

## issue 正文

- 首段写目标：这件事完成后什么行为会改变。
- 需要拆分的工作写成任务列表，每项挂 issue 编号；完成时在正文中打勾，不另发评论记录进度。
- 前提条件、参考资料写在正文里，随实际情况修改正文，不靠评论追加。

## 评论

### 结构

```markdown
设计文档：`docs/plans/<文件>.md`（<提交号>）。<一句话说明文档内容>

#### 已确定

- <结论>。<理由，一句>

#### 未确定

- <问题>。<当前采用的处理>

#### 待确认

- <事实>。<怎样确认>
```

- 没有内容的节整节省略。只有一项时可以不分节，写成一段。
- 已确定：写结论和一句理由，理由指向本项目的约束或已有事实。
- 未确定：写清楚待选的几种做法，以及在定下来之前按哪一种处理。
- 待确认：写尚未证实的事实和确认方式。状态用摘录文档的四档词：已确认、部分待确认、折中实现、待清理；不另造「待验证」这类词。

### 更正

更正已有结论时，评论首句写「更正：」加新结论，随后写依据。若更正的是 issue 正文中的说法，同时修改正文。

### 出处

参考了外部插件、资料或实测记录时，结论的主语仍是本项目或目标游戏，出处以链接或「参考：」附在句末，不作为句子主语。不写「作者已验证」「已实机确认」这类出处说明；需要说明可信度时用上面的四档状态词。

### 数字

只保留读者做判断需要的数字，例如通道数、取值范围、默认值。样本数、覆盖率、统计占比不写，确有必要时写进 `docs/plans/`。

### 内部编号

设计文档中的决定编号（如 D6）不出现在评论中。评论直接写出该决定的内容。

## 改写对照

以外部资料为主语、附带验证出处，改为以结论为主语。

```markdown
# 前
RE4R-ShapeKey-System 使用了两种信号来源，作者已在游戏中验证。

# 后
更正：RE4R 有可用的表情信号来源：头部网格上由游戏写入的修正形态键权重，以及面部骨骼姿态。
参考：[RE4R-ShapeKey-System](https://github.com/Funnyguysmz/RE4R-ShapeKey-System)
```

复述讨论经过，改为结论。

```markdown
# 前
一开始的想法是运行时遇到查不到的信号就当 0 处理，但这等于把问题留给了玩家，所以改成……

# 后
- 信号字典必须列出全部通用信号名，本游戏没有的写 `"raw": null`。缺口在接入游戏时处理，不在运行时兜底。
```

## 自检

1. 不读讨论经过，能否从评论得知当前状态。
2. 是否重复了文档、提交信息或正文中已有的内容。
3. 句子主语是否为本项目或目标游戏，而非外部资料。
4. 是否残留验证出处、样本数或内部编号。
5. 进度变化是否已经更新到 issue 正文的任务列表。
