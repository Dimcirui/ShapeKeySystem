# 发布说明规范

本规范适用于 GitHub release 正文和 mod 发布页的更新说明。读者是插件使用者，不是维护者：发布说明回答「这一版我能多做什么、原来哪里不对、哪里修好了、要不要改自己的配置」。打包流程见 `tools/package.ps1`（#8），本文只管正文怎么写。改编自 EFX-Editor 的 `docs/writing/release_guideline.md`。

措辞约束与面板文案同源：只写结论，不写出处、验证过程和日期。

## 核心判断

一条发布说明应当让使用者读完就知道这项变化对自己意味着什么。如果一条内容只有维护者关心（重构、测试、注释、内部命名），它不进发布说明。

发布说明按使用者可感知的变化归并，不按提交逐条罗列：五个提交共同完成一项功能，只写一条；一个提交里有两项可感知的变化，写两条。

## 结构

```markdown
# ShapeKeySystem X.Y.Z

## ⚠️ 不兼容变更
## 新增
## 变更
## 修复
```

- 标题固定为 `# ShapeKeySystem X.Y.Z`。
- 没有内容的节整节省略。「不兼容变更」只在需要使用者采取行动时出现，例如用户 profile 需要修改、旧绑定不再读取、需要另装依赖。只有一项且与某条「变更」直接相关时，可以写在该条内并加粗，不单独开节。
- 不写安装说明节。安装方式在 README 里维护，只在安装方式本身变化时写进「新增」或「不兼容变更」。

## 分节判据

- **新增**：插件本身新增的功能、新支持的游戏、新的内置配置。
- **变更**：内置配置和信号映射的订正、默认值调整，以及不改变能力、只改变用法的界面调整。
- **修复**：插件自身的错误，例如保存丢值、换装后不再驱动、面板报错。

## 条目写法

一条一行，格式为 `- **对象**：一句话结论`。对象是面板页名、功能名或配置名，与界面上的名称一致。

- 写结果，不写机制：写「换装后保留未保存的映射修改」，不写重扫和缓存怎么处理。
- 不写内部字段名和实现细节。字段名只在使用者会在界面或配置文件里看到它时出现。
- 不写资料来源：其他插件、逆向笔记、实测记录都不出现。使用者只需要知道现在能做什么。
- 不确定性写成作用未知，不写成验证状态：写「效果因模型而异」，不写「尚未确认」「待实机验证」。
- 近似与限制只在使用者可能被误导时写一句。

**大型功能**可以单开 `###` 小节：一到两句总述，然后是条目列表，每条仍是一行。一版里至多一两个这样的小节；其余内容按普通条目写。

## 篇幅

普通版本每节一到三条，全文控制在上一版的长度以内。写完与上一版对比，超过一倍就是写多了。含大型功能的版本例外，但每个 `###` 小节同样不超过十条。

## 改写对照

条目解释了错误的成因，改为只写现象与结果。

```markdown
# 前
- 新建的表情配置保存后读不回来：REFramework 把空 Lua 表写成 JSON null，读取时被当成无效文件跳过。

# 后
- **表情配置**：新建的空配置保存后可以正常打开
```

需要使用者行动的变更，把行动要求写在条目内并加粗。

```markdown
- **输入法**：改用 REF-IME，不再使用差分管理器的 UI DLL。**需要另装 REF-IME。**
```

## 自检

1. 每一条是否是使用者可感知的变化，没有重构、测试、注释类内容。
2. 分节是否符合判据。
3. 是否残留出处、验证状态或日期：

   ```bash
   grep -cE "实机|已确认|尚未确认|已验证|待验证|20[0-9][0-9]-" <notes>   # 应为 0
   ```

4. 长度是否在上一版的一倍以内。
