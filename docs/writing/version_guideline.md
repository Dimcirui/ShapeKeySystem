# 版本规范

本规范说明 ShapeKeySystem 什么时候升版本、升哪一位，以及版本号和发布说明怎样配合。版本号是给使用者看的：「设置与调试 → 关于」里的版本历史、mod 发布页上的版本、GitHub release 的 tag，指的都是使用者能下载到的东西。

## 核心判断

版本号跟着发布走，不跟着合并走。一个 PR 合进 main 不升版本；打包发布时才定版，一次定版包含上次发布以来的全部改动。

这样做的原因：

- 按 PR 升版本，会出现没人能下载到的版本号。
- 多人并行开发时，每个分支都改 `Version.lua` 的同一行，合并必然冲突。
- 重构、测试、部署脚本这类改动使用者感知不到，不该占一个版本号。

## 哪一位

一次发布取其中最高的一级。只要包含一项新功能就升 minor，不论同时有多少修复。

| 位 | 什么时候升 | 例子 |
|---|---|---|
| major | 使用者已有的文件不能照常使用，且插件不做迁移；或公开接口（`ShapeKeySystemAPI`）不兼容地变化 | 绑定文件格式改变且不迁移；移除一项功能 |
| minor | 新增能力，旧文件照常可用 | 支持新游戏、新的面板功能、新的内置配置、新的条件类型 |
| patch | 不增加能力，只修正错误或订正已有内容 | 面板报错、换装后不再驱动、信号映射订正、文案调整 |

补充规则：

- **需要使用者行动的变化至少升 minor**，例如需要另装依赖、需要修改自己的配置。发布说明里写「不兼容变更」（见 [release_guideline.md](release_guideline.md)）。
- **有迁移就不算 major**：设置字段改名但插件自动迁移，按变化本身的性质定级。
- **公开接口有自己的版本号**，定义在 `API.lua`，只随接口变化，与插件版本无关。
- 只改维护者关心的内容（重构、测试、注释、工具），不发布，也不升版本。

## 平时：积攒发布说明

每个包含使用者可感知变化的 PR，在 [docs/releases/unreleased.md](../releases/unreleased.md) 对应的小节加一行，写法按 [release_guideline.md](release_guideline.md) 的条目格式。同一项功能分几个 PR 完成时，后面的 PR 改写已有条目，不追加新行。

只有维护者关心的 PR 不写。

## 定版

1. 在 main 上整理 `unreleased.md`：合并重复条目，删掉空的小节，按上表确定版本号。
2. 改 `Core/Version.lua`：`V.number` 改为新版本号，在 `V.history` 最前面加一条。`notes` 是一句话，只写这一版最主要的一两项变化，例如 `支持鬼武者·剑之道；新增面部动画测试`。
3. 单独提交：`chore(version): 定版 X.Y.Z`（见 [commit_guideline.md](commit_guideline.md)）。
4. 在这个提交上打 tag `vX.Y.Z`，用 `unreleased.md` 的内容建 GitHub release，标题改为 `# ShapeKeySystem X.Y.Z`。
5. 把 `unreleased.md` 清回空模板，和下一个改动一起提交即可。

## 自检

1. 这次发布是否包含使用者能感知的变化；没有就不发布。
2. 版本号是否取了这批改动里最高的一级。
3. 需要使用者行动的变化，是否至少升了 minor，并在发布说明里写明。
4. `Version.lua` 的 `notes` 是否只有一句话。
